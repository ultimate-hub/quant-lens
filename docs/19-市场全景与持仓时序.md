## 一、市场全景热力图

### 它长什么样

Finviz 风格的树状图（treemap）：

- **每个矩形 = 一只股票**
- **面积 = 市值**（或等权，可切换）
- **颜色 = 今日涨跌幅**（红涨绿跌，幅度越大颜色越深）
- **分组 = 行业**，一个行业是一个大块，里面嵌着个股

放在首屏，打开软件第一眼就看得到。

### 数据从哪来

用东方财富的**批量行情接口**：

```
GET push2.eastmoney.com/api/qt/ulist.np/get
    ?secids=1.600519,0.000858,116.00700,105.AAPL
    &fields=f12,f14,f2,f3,f20
```

| 字段 | 含义 |
|---|---|
| f12 | 股票代码 |
| f14 | 名称 |
| f2 | 最新价 |
| f3 | 涨跌幅 % |
| f20 | 总市值 |

**为什么不用现有的 `registry.get_snapshot()`**：
那个是「一只股票一次请求」。144 只要 144 次请求，太慢而且容易被限流。
批量接口一次能查 50 只，3 次就搞定 —— 实测全部抓完 0.2 秒。

### 分组是怎么定的

一只股票要有归属的行业才能进热力图。查找顺序：

1. **概念库里 `kind='industry'` 的直接归属**（主路径）
2. **按概念兜底映射推断**（`_CONCEPT_FALLBACK` 表）
3. 都没有 → 归到「其他」

第 2 步是为什么加的：概念库里有 26 个「概念」（跨行业主题，比如"固态电池""机器人"），
它们不绑定行业。如果只走第 1 步，有 **63 只股票**会掉进「其他」这个大筐。

实测把兜底映射加上之后：

| | 加之前 | 加之后 |
|---|---|---|
| 「其他」股票数 | 63 只 | **0 只** |
| 行业分组数 | 25 个 | 30 个 |

兜底表长这样：

```python
_CONCEPT_FALLBACK = {
    "固态电池": "电力设备", "机器人": "机械", "创新药": "医药", ...
}
```

**只影响热力图分组，不动概念库本身的数据。**

### 为什么要有「按市值 / 等权」切换

按市值排的话，8 只美股科技巨头占了整张图的 **37%** ——
苹果一家 5 万亿美元，比整个 A 股白酒板块还大。

这是真实的市值分布，没造假。但结果是 A 股的中小盘被压成指甲盖大小，看不清。

所以加了个等权模式：每只股票算一份，面积反映的是**家数**。
想看「今天哪类股票在涨」用等权，想看「市值权重的影响」用按市值。

### 每日封面

每天第一次打开时抓一次，存进 `market_snapshots` 表：

```sql
CREATE TABLE market_snapshots (
    day        TEXT PRIMARY KEY,   -- 2026-11-08
    payload    TEXT NOT NULL,      -- 完整 JSON
    created_at TEXT
);
```

当天再打开直接用缓存（3 毫秒 vs 200 毫秒）。这样做有两个好处：

1. **「今天的封面」一整天不变** —— 盘中刷新价格会导致截图前后不一致
2. **避免频繁请求** —— 刷新按钮点多了会被东财限流

点「下载封面图」会把当前视图导出成 PNG（2 倍分辨率），可以直接发朋友圈。

## 二、持仓日志

### 为什么不做成"持仓管理"

一个常见的误区是把持仓做成"只能有一只股票一条记录"。
但**分批建仓是常态** —— 同一只股票在 3 个不同价位买入，如果合并成一条，
买入时间就丢了，止盈止损的参考基准也算不准。

所以：

- 每条记录 = **一次买入**
- 同一只股票可以有多条
- 界面上可以按「股票汇总」或「按买入记录」两种视角切换

### 数据模型

```sql
CREATE TABLE positions (
    id           INTEGER PRIMARY KEY,
    symbol       TEXT,        -- 600519.SH
    name         TEXT,
    buy_date     TEXT,        -- 2026-03-01
    buy_price    REAL,
    shares       REAL,        -- 为什么是 REAL 见下
    target_ratio REAL,        -- 目标占比 %
    note         TEXT
);
```

**为什么股数用 REAL 而不是 INTEGER**：

| 市场 | 最小交易单位 |
|---|---|
| A 股 | 100 股（1 手） |
| 港股 | 每手股数不同，且有碎股 |
| 美股 | 可以买零股（0.001 股） |
| 场内基金 | 按份 |

用浮点兼容所有情况，显示时再按市场格式化。

### 盈亏怎么算

```
成本 = 买入价 × 数量
市值 = 当前价 × 数量
浮动盈亏 = 市值 - 成本
收益率 = 浮动盈亏 / 成本
占比 = 该股总市值 / 全部持仓总市值
```

**只算浮动盈亏，不算已实现盈亏** —— 因为没做卖出记录。
这个工具的定位是「当前持仓快照」，不是完整的交易账本。想做完整账本要再加一张
trades 表，那是另一个量级的工作。

### 取价失败怎么办

持仓里有股票停牌、代码写错、或者接口挂掉时，取不到当前价。

**处理方式：用买入价代替，并标记 `price_ok=False`，界面上打个「估」字标。**

宁可显示「这个数不确定」，也不给一个看起来精确但错的数字。
汇总里还会单独统计「几笔取价失败」。

### 目标配比

用户可以为每只股票设一个目标占比（比如 25% 表示希望占四分之一）。

界面上的配比图会把**实际占比**画成条形，**目标占比**画成灰色虚线。
差值自动算出来：

- 实际 31%，目标 25% → 显示「超 6%」
- 实际 12%，目标 25% → 显示「低 13%」

这就是调仓的依据。没有目标值就不做对比，不会强行给建议。

## 三、区间显示改造

### 改之前

原来的三张卡片：

```
悲观情景  1,218.78  -15.7%
中性情景  1,490.99   +3.1%
乐观情景  1,869.35  +29.2%
```

问题：**`-15.7%` 和 `+29.2%` 让人误以为是两个独立的目标价**，
而不是"价格有 5% 概率低于 1,218，有 5% 概率高于 1,869"。

数字看着精确，但它的含义是概率分位数，不是点位。

### 改之后

一条比例尺 + 两组区间：

```
20 个交易日后的价格区间                    起点 1,446.44
├────────────●────────────┤      90% 区间
     ├──────●──────┤             50% 区间

90% 区间（5% ~ 95%）   1,270.71 ~ 1,823.94   -12.2% ~ +26.1%
50% 区间（25% ~ 75%）  1,384.41 ~ 1,614.12    -4.3% ~ +11.6%
中位路径（50% 分位）   1,487.77              +2.9%
```

比例尺按 90% 区间铺满，50% 区间按真实比例缩在里面，中位数是一根竖线。

**这样一眼就能看出"窄的那段"和"宽的那段"的关系**，
而不是三个孤立的数字。

## 四、时序预测模型

### 先说清楚预期

日频股价近似随机游走。这是金融时间序列里的共识，不是我保守。

所以这个模块的目标**不是造一个很准的模型**，而是：

> 把几个主流方法都跑一遍，用真实的样本外误差比出谁更好，**如实告诉用户**。

如果所有模型都没跑赢随机游走，界面会直接说「没有任何模型显著优于随机游走」，
而不是硬拿一个模型画线骗人。

### 五个模型

全部用 numpy 实现，没有引入任何统计库：

| 模型 | 做法 | 说明 |
|---|---|---|
| **随机游走** | 明天 = 今天 | **基准**，不是凑数的 |
| 带漂移 | 今天 + 历史平均日涨幅 × h | 假设趋势按平均速度延续 |
| Holt 阻尼趋势 | 指数平滑 + 阻尼趋势 | 在对数价格上跑，保证预测为正 |
| OLS 趋势外推 | 对数价格对时间做最小二乘 | **最容易翻车的一个** |
| AR(5) | 对**收益率**做 5 阶自回归 | 直接对价格做 AR 等价于随机游走，所以建模收益 |

### 为什么 OLS 最容易翻车

实测（同一批数据、5 个检验窗口）：

| 股票 | OLS 相对基准 |
|---|---|
| 600519.SH 茅台 | **+7.6%**（赢） |
| 002594.SZ 比亚迪 | **-474%**（输得离谱） |
| AAPL.US 苹果 | **-191%** |
| 300750.SZ 宁德时代 | **-125%** |

强趋势样本上，直线外推会推出完全脱离现实的价格
（实测有模型预测出比现价低 60% 的结果）。

**处理：所有模型预测的累计涨跌幅都被夹在 ±40% 内。**

不是为了美化结果，而是「一支股票 20 天腰斩」这种预测在实盘里没有决策价值。

### 关键：必须用多窗口回测

**这是最容易做错的地方。**

如果只挖掉最后 20 天做检验，**谁在这 20 天碰巧猜对谁就赢**，完全是运气。

实测对比（同一只茅台，同一批模型）：

| 回测方式 | 最佳模型 | 结论 |
|---|---|---|
| 单窗口 | OLS 趋势外推 | 改善 22.5% |
| **5 窗口平均** | **Holt 阻尼趋势** | **改善 25.1%** |

**单窗口选出来的"最佳模型"和 5 窗口选出来的根本不是同一个。**

所以 `backtest()` 默认跑 5 个不重叠的检验窗口，取平均误差：

```python
for w in range(windows):
    end = n - w * holdout          # 从最近往前推
    start_test = end - holdout
    train = y[:start_test]         # 只用测试窗口之前的数据训练
    # 各模型预测 holdout 步，和真实值比
```

### 「可用」的判定门槛

不是跑第一名就说它好。要求 **MAE 比随机游走改善 3% 以上**才算可用。

为什么是 3%：单窗口时 2% 的提升都可能纯属运气，
多窗口平均后 3% 才算有点东西。门槛低的话，等于给随机波动找解释。

实测：

| 股票 | 最佳模型 | 相对基准 | 判定 |
|---|---|---|---|
| 茅台 | Holt | +25.1% | 可用 |
| 苹果 | AR(5) | +11.1% | 可用 |
| 比亚迪 | 随机游走自己 | 0% | **不可用** |
| 宁德时代 | Holt | +0.84% | **不可用** |

**一半的股票上，没有任何模型跑赢随机游走。** 界面会如实显示这一点。

### 方向命中率为什么随机游走是「—」

随机游走永远预测"持平"，没有方向。统计方向命中率时它的预测符号恒为 0，
和真实涨跌（±1）比对永远是 0 分。

这是定义问题，不是它表现差。所以随机游走这一栏的方向命中率显示为「—」，
不参与排名，也不会因为这个 0 分被误判成"最差模型"。

### 界面上怎么用

- 时序模型表显示 5 个模型的 MAE / MAPE / 方向命中 / 相对基准
- **只有真的跑赢基准的模型路径才会画到扇形图上**（黄色虚线）

不赢基准还画出来，就等于拿一条没有依据的线误导人。

- 表下面明确写着「模型排名依赖样本区间，换一段时间可能完全不同」

## 五、这一轮踩的坑

### 1. PowerShell 里跑多行 Python 一定失败

```
& $py -c "import sys
for x in ...:"
```

PowerShell 会把多行字符串参数搞坏，报 `只应将 ScriptBlock 指定为 Command 参数值`。

**结论：写脚本到文件再执行，不要内联。**

### 2. 运行时的 certifi 路径会失效

某次重启服务后所有 K 线请求报：

```
OSError: Could not find a suitable TLS CA certificate bundle,
invalid path: ...\certifi\cacert.pem
```

原因是开发环境的 Python 运行时被升级替换了，`site-packages` 里的 certifi 没了。

**教训：项目依赖要装进自己的 `.venv`，不要依赖外部运行时。**
（`install.bat` 的做法是对的，这次是我图省事用了系统解释器。）

### 3. 删除代码块时把外层结构一起删了

改 `drawFanChart` 时用字符串替换，把结尾的 `export function dispose() {`
一起替换掉了，导致函数体失去声明 → `Unexpected token '}'` → 整个分析页白屏。

**教训：替换带结尾的代码块后，一定要做语法检查。** 这次是拿 node 的 `--check` 扫出来的。
