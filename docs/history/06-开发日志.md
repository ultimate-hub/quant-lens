| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 | `python --version` | Python 3.13.14 ✅ |
| 2 | `pip --version` | pip 26.1.2 ✅ |
| 3 | `git --version` | git 2.55.0 ✅ |
| 4 | `python -m venv .venv` | ❌ 失败：ensurepip 报错 |
| 5 | 尝试 `uv` | ❌ pip 装不上 |
| 6 | 尝试 `virtualenv` | ❌ pip 装不上 |

**根因诊断**（花了最长时间）：
- 现象：所有 pip 安装都失败，报 "Could not find a version"
- 测试：`Invoke-WebRequest https://pypi.tuna.tsinghua.edu.cn` → 失败
- 测试：`Test-NetConnection pypi.tuna.tsinghua.edu.cn -Port 443` → **True**（TCP通！）
- 测试：Python `urllib.request.urlopen(...)` → **HTTP 200**（Python 能通！）
- 检查：`$env:HTTPS_PROXY` → `http://127.0.0.1:7897`

**结论**：系统配置了代理，但代理软件没运行。
PowerShell 的 `Invoke-WebRequest` 走代理 → 失败；
Python 的 `urllib` 在某些情况下绕过代理 → 成功。

**最终解决**：
1. 改用系统内置的 Python 3.12 运行时（`C:\Users\杨\.dsh\dsh-runtimes\...`）
2. 清除代理环境变量后安装
3. 配置清华镜像源

> **经验教训**：排查网络问题时，一定要分层测试：
> DNS → TCP → TLS → HTTP → 应用层。
> 直接看"请求失败"是没用的，要找到具体哪一层断了。

### 阶段二：技术选型调整（关键决策）

**原计划**：用 `akshare` 库抓数据。

**问题**：akshare 依赖链太长，安装耗时超过 1 小时仍未完成。

**决策**：直接对接东方财富/腾讯的底层接口。

**理由**：
- akshare 底层抓的就是这些接口
- 少一层依赖 = 少一类故障点
- 数据源改版时，我们能立即自己修，不用等库作者发版

**代价**：需要自己处理接口的坑（分页、限流、字段格式）。

**结论**：✅ 值得。最终同步一只基金只需 0.79 秒。

### 阶段三：数据源攻坚（最有技术含量的部分）

#### 坑1：F10 接口只给 20 条

```
请求 pageSize=200 → 实际返回 20 条
TotalCount=3911 → 需要 196 页
```

**解决**：改用 `pingzhongdata` 接口，一次请求返回全部历史（3911条 / 0.2秒）。

**技术细节**：该接口返回的是 JavaScript 代码而非 JSON，需要用正则表达式提取数组：
```python
m = re.search(r"Data_netWorthTrend\s*=\s*(\[.*?\])\s*;", text, re.S)
nav_list = json.loads(m.group(1))
```

**效果**：196 次请求 → **1 次请求**，提速约 200 倍。

#### 坑2：东方财富限流

开发中途，`push2his.eastmoney.com` 开始返回：
```
RemoteDisconnected: Remote end closed connection without response
```
重试 3 次全部失败，`urllib` 和 `requests` 都一样 → IP 级限流。

**解决**：切换到腾讯财经作为主通道，东财降级为备用。

**设计模式**：`try 主通道 / except 用备用通道`
这就是"容错设计"，是生产级软件的标配。

#### 坑3：腾讯接口单次最多 800 条

实测：
```
n=640  → 641 条 ✅
n=800  → 801 条 ✅
n=1000 → 641 条 ⚠️（静默降级，不报错，最危险）
n=3000 → param error ❌
```

**注意 `n=1000` 的情况**：服务器不报错，但只给你 641 条。
如果代码不检查，会**悄悄丢数据** —— 这是最危险的 bug 类型。

**解决**：倒序分页。从今天往回，每次拉约3年，直到覆盖起始日期。

### 阶段五：联调与真实 Bug

#### Bug1：图表被压成一条竖线 ⭐

**现象**：指标卡片正常显示，但净值图只有左边一条密集的竖线。

**根因**：
```javascript
renderFund(data);   // 此时容器还是 display:none，宽度=0
show('result');     // 到这一步才显示
```

ECharts 在 0 宽度的容器里初始化，所有点挤在 x=0。

**修复**：
```javascript
show('result');     // 先显示
renderFund(data);   // 再初始化
[navChart, ddChart, scoreChart].forEach(c => c && c.resize());  // 再测量
```

**通用规律**：所有图表库（ECharts/Chart.js/D3/Plotly）在隐藏容器里初始化都会出问题。
做标签页切换、折叠面板时会反复遇到。

#### Bug2：股票接口请求了两次（手误）

代码里不小心写了两行 `_get_json(url, ...)`，第一个没带参数。
虽然不影响结果（第二次覆盖），但浪费一次网络请求。
已删除。

## 关键决策复盘

| 决策 | 备选方案 | 为什么这样选 |
|---|---|---|
| 直接用底层接口 | akshare | 依赖少、可控、快 |
| SQLite | PostgreSQL | MVP阶段零配置，单文件备份 |
| 原生HTML | Vue/React | 零构建，先验证需求 |
| ECharts本地文件 | CDN | 国内CDN不稳定 |
| 主备双通道 | 单一数据源 | 抗限流、抗改版 |
| 分段倒序抓取 | 一次请求 | 接口硬限制800条 |

## 如果重做一次，会怎么改

1. **更早做网络分层诊断** —— 花了1小时在 pip 上，其实一个 `Test-NetConnection` 就能定位
2. **数据源先做可用性探测脚本** —— 把候选接口都测一遍再写代码
3. **图表先做一个最小demo** —— 验证 ECharts 在目标环境下能正常渲染
4. **单元测试和数据代码同步写** —— 这次是后补的，如果指标公式写错，回测结论全错
