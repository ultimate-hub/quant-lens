## 三、踩到的坑（真实排障记录，很有教育意义）

### 坑1：虚拟环境创建失败

**我想做的**：创建一个"虚拟环境"（venv）——相当于给这个项目单独开一间小厨房，装自己的一套厨具，不污染系统。

**现象**：
```
python -m venv .venv
→ Error: ensurepip returned non-zero exit status 1
```

**原因**：Microsoft Store 版 Python 在**中文用户名路径**（`C:\Users\杨\...`）下创建虚拟环境有已知 bug，pip 引导程序启动失败。

**尝试的替代方案**：
- `uv`（新一代包管理器）→ pip 网络受限装不上
- `virtualenv` → pip 报 "Could not find a version"，同样装不上

**为什么 pip 装不了包**：当时用的 pip 源是国外 PyPI（Python Package Index，官方包仓库），当前网络环境访问受限。

### 坑2：网络与镜像源

**解决思路**：换用**清华镜像源**（PyPI 的国内完整拷贝，速度更快且不受限）：
```
pip install xxx -i https://pypi.tuna.tsinghua.edu.cn/simple
```
商店版 Python 依然失败，但换用系统里另一套内置 Python（3.12）后，安装可以正常进行——akshare 及其依赖正在通过清华源后台安装。

**教训（通用规律）**：国内做 Python 开发，第一步永远是配国内镜像源，能避免 90% 的"装不上包"问题。

## 四、最终采用的环境方案

| 组件 | 位置 |
|---|---|
| Python 3.12（内置运行时） | `C:\Users\杨\.dsh\dsh-runtimes\...\python.exe` |
| 额外安装的库 | 同目录 site-packages（akshare、fastapi、uvicorn 等） |
| 镜像源 | 清华 TUNA |

> 为什么不用虚拟环境了？MVP 阶段优先"能跑通"，环境隔离是工程洁癖，后续商业化部署时（换 Linux 服务器）会重新做规范的 Docker 隔离。

## 五、你要能复述的要点

- Python = 语言的解释器；库 = 别人写好的功能包；pip = 下载库的工具
- 镜像源 = 官方仓库的国内加速拷贝
- 虚拟环境 = 项目独立的"小厨房"（本机因路径中文问题暂不用）
